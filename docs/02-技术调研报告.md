# DataClaw 二期技术调研报告

> 调研对象：汉得灵舟·DataClaw（企业级数字员工平台）二期技术选型
> 调研时间：2026-10-23（所有 Star/Fork/License/最近提交均为当日检索值）
> 调研人：开源生态技术调研员
> 配套材料：`docs/research/notes.md`（检索原始笔记）

## 0. 一句话结论

**不要 fork 任何一个开源 Agent 平台来做 DataClaw 的底座。** 推荐走「组合式自研」：自研一层很薄的**员工/会话/技能/数据权限内核**（Java 为主 + Python 解析与 SQL 改写 sidecar），运行时沙箱直接用 **OpenSandbox**（K8s + Firecracker，Apache-2.0），数据权限用 **sqlglot AST 改写 + OPA 策略 + 结果兜底脱敏**，文档解析复用 **Docling / MinerU**，RAG 若必须现成则只把 **RAGFlow** 当"解析+检索引擎"放在自有权限网关后面，BI 用 **语义层 + ECharts 模板**，渠道（飞书/企微/钉钉）自研适配层。理由一句话：**DataClaw 真正卖的是"企业数据面 + 员工资产化 + 中国 IM + 结算与审计"，这四样恰好是所有开源 Agent 平台都不提供的；而它们提供的（可视化编排、RAG、插件市场）反而是最容易补的。**

## 0.2 先修正三个前提（否则选型会跑偏）

### 前提一：OpenClaw 在 2026-10 已经不是"纯个人玩具"

PDF 里"个人版龙虾 = 手动配置、无隔离、无员工管理"的对比，在今天的 OpenClaw 上**部分已经不成立**。官方文档明确写了团队部署：一个 Gateway 服务全团队、operator roles 绑定认证身份、会话有 creator/owner/prompter 三层归属、支持 per-agent 沙箱、有 ClawHub 技能市场与扫描。官方原话是"team operation is configuration, not a separate edition"。

**这意味着什么**：如果 DataClaw 的对客材料继续用"他们没隔离、没管理"来做对比，懂行的客户（尤其是看过 OpenClaw 文档的技术负责人）会当场质疑，反而伤害可信度。**建议把对比维度整体挪到"企业数据面"**：行列级数据权限、中国 IM 渠道、员工模板/版本/分配/回收、统一算力结算、私有技能市场的合规审核与追责。这五件事 OpenClaw 到今天也没有，而且是企业采购真正的决策点。

### 前提二：开源平台的"多租户"≠ 企业级多租户

这是本次调研最重要的发现，直接决定"能不能 fork"：

- **Dify** 的 License 写得很直白：未经书面授权，"you may not use the Dify source code to operate a multi-tenant environment"，而 Dify 里"一个 tenant 就是一个 workspace"；同时"不得移除或修改前端 LOGO 与版权信息"。DataClaw 要做多租户 + 白标，**两条同时踩**。
- **FastGPT** 同类限制：不得运营"similar to the FastGPT"的多租户 SaaS；不得改 LOGO。
- **Dify 社区版 Agent 运行时**官方自己承认：文件访问控制"**not intended to provide a hardened security boundary between mutually untrusted users or workloads**"。
- **Coze Studio** README 直接提示公网部署风险：开放注册、代码节点 Python 执行环境、SSRF、部分 API 水平越权。

**结论**：fork Dify/FastGPT 做商业多租户产品，要么买商业授权（成本与话语权都不在自己手里），要么改到"面目全非"再承担许可证风险。这不是技术问题，是商业模型问题。

### 前提三：数据权限没有"开箱即用"的开源答案

调研了 Ranger、Sentry、ShardingSphere、Casbin、OPA、DataHub、OpenMetadata 之后可以明确说：**没有任何一个开源件能同时覆盖"任意数据库 + AI 自由查询 + 行/列/字段级 + 可审计"**。

- Apache Ranger 强在策略管理与 Hive/HDFS/Trino 等大数据插件，但**不是 MySQL/PG 的 SQL 网关**，管不到业务库的即席查询。
- Apache Sentry 已经归档（最后 push 2020-07），功能并入 Ranger，**不要再选**。
- ShardingSphere 的脱敏是"代理层 SQL 改写"，能做列脱敏，但它不做行级授权，也要求流量走它的 Proxy/JDBC。
- Casbin/OPA 是"决策库/决策服务"，不碰 SQL，得自己写执行点。

**所以数据权限必然是自研 + 组合，不能指望"接一个开源件就完事"**。这也正好是 DataClaw 最该建立壁垒的地方。

## A. 个人级 Agent 本体：OpenClaw 到底是什么

### A.1 基本盘（已核验）

- 仓库：<https://github.com/openclaw/openclaw>，**392,832 Star / 82,565 Fork，MIT，TypeScript**，最近 push 2026-10-23。
- 定位（README 原文）：开源 AI 助手，跑在用户自己的电脑上，在 Discord、iMessage、Slack、Teams、Telegram、WhatsApp 等 20+ 渠道出现；提供 macOS/iOS/Android/Windows/Linux 原生客户端；"一个 Gateway 既能当个人助手，也能做团队部署，差别只在配置"。
- 治理：OpenClaw Foundation（独立 501(c)(3)），无付费版、无托管服务、无代币；发布物签名。

> 关于名字：任务里说的 Clawdbot / Moltbot 是它的前身名（社区常称"龙虾"）。仓库现名 `openclaw/openclaw`；旧名迁移细节我**未逐一核实**，以官方仓库与 openclaw.org 为准。

### A.2 架构（官方文档 `concepts/architecture`）

一句话：**Gateway 是本地控制面，Agent 是执行面，Channel 是入口，Node 是设备，Skill 是"教它怎么用工具"的说明书。**

- **Gateway（守护进程）**：持有全部消息面连接（WhatsApp 走 Baileys、Telegram 走 grammY、Slack/Discord/Signal/iMessage/WebChat），对外暴露类型化 WebSocket API（默认 `127.0.0.1:18789`）；校验入站帧（JSON Schema）；发出 `agent/chat/presence/health/heartbeat/cron` 等事件。
- **协议**：文本帧 JSON，首帧必须 `connect`；之后 `{type:"req",id,method,params}` → `{type:"res"}`；事件 `{type:"event"}`；副作用方法要求幂等键；连接要签 `connect.challenge` nonce；新设备需配对，发 device token。
- **Clients**：macOS App / CLI / Web Control UI / 自动化。
- **Nodes**：macOS/iOS/Android/headless 以 `role:node` 连同一个 WS，声明 caps/commands（camera、screen.record、location.get 等），设备级配对。
- **扩展面**：Tools、Skills、Plugins（约 150 个插件 SDK 入口）、MCP client + MCP server、A2A 1.0、ACP、OpenAI 兼容 API、OpenTelemetry/Prometheus。

**这套架构值得抄的地方**：把"渠道连接"和"Agent 执行"拆开、把"工具执行"下沉到可替换沙箱、把"设备能力"抽象成 node。DataClaw 的"Channel 接入层"和"运行时层"分界，可以直接照这个思路。

### A.3 Skill 机制（`tools/skills`）

- **形态**：一个目录 + `SKILL.md`（YAML frontmatter + Markdown 正文），目录里可以带脚本、模板、参考资料。
- **加载优先级（高→低）**：workspace `skills/` → project `.agents/skills` → personal `~/.agents/skills` → managed `<state-dir>/skills` → workshop → bundled → extraDirs/插件技能。同名技能高优先级覆盖低优先级。
- **加载时过滤**：按环境变量、配置、二进制是否存在做 gating；支持 per-agent allowlist；支持"个人技能"在共享网关上按身份与版本隔离，未显式共享前不进团队。
- **技能市场**：ClawHub（clawhub.ai），有发布、审核、安全审计、按版本的信任判定；扫描来自 VirusTotal、ClawScan 与静态分析。

**判断**：`SKILL.md` 这套"Markdown 说明书 + 目录化资源 + 渐进加载"已经是事实标准（Anthropic Agent Skills 同源，见 D 节）。DataClaw 的技能包**必须兼容这个格式**，否则生态进不来；但企业版要在它之上加"权限声明 + 签名 + 审核 + 版本锁定"。

### A.4 沙箱与安全现状（官方自述，很关键）

- **默认关闭**："Sandboxing is off by default"；Gateway 永远在 host，只有工具执行进沙箱；官方明确"这不是完美的安全边界，只是在模型犯傻时限制文件系统与进程访问"。
- **后端**：Docker（默认）、Podman、SSH、OpenShell、Crabbox（云盒子）。
- **信任模型**："一个 Gateway = 一个信任域"。能给 tool-enabled agent 发消息的人，共享这个 agent 的工具授权；要服务互不信任的人或组织，官方建议**一个租户一个 Gateway**。
- **密钥**：受保护密钥可以用 handle + 出站替换，让模型上下文里看不到明文；但"agent 可读条目、宿主访问、允许服务的响应"仍有暴露面。
- **技能供应链**：ClawHub 会扫描，但官方承认"扫描未完成或过期时，可以带警告安装"；`openclaw skills verify` 校验的是注册中心的验证信封，**不对本地当前文件做 hash**。

### A.5 为什么企业化难（六条，逐条给依据）

1. **隔离粒度与成本矛盾**：一个 Gateway 一个信任域 → 要真隔离就得"每租户/每员工一套 Gateway + 一套沙箱"，运维成本随人数线性上涨。DataClaw 的"每用户独占容器"方向是对的，但必须解决"空闲回收 + 预热池"，否则 500 人就是 500 个常驻容器。
2. **默认不安全**：沙箱默认关、工具默认在 host 跑。企业交付不能靠"记得开"。
3. **数据权限缺位**：OpenClaw 管的是"工具能不能调"，不管"查哪几行、看哪几列"。这是 DataClaw 场景（工时、销售、合同）的刚需。
4. **中国 IM 缺位**：官方渠道列表里没有飞书/企微/钉钉。这不是"加个适配器"那么简单，涉及回调加密、主动消息额度、卡片交互、组织架构同步（见 H 节）。
5. **资产化缺位**：OpenClaw 有 agent、有技能、有团队角色，但没有"公共员工模板 → 版本 → 分配给谁 → 回收"这套 HR 语义。DataClaw 的"数字员工"叙事必须自己实现。
6. **结算与审计缺位**：没有"按员工/按部门计量 token 与算力、出账单"的能力；审计也偏"运行可观测"，不是"合规审计"（谁、在什么权限下、查了什么数据、输出了什么）。

### A.6 能不能直接当底座？

**不能，但值得"借三层"。**

- 不建议 fork 全量：Node/TS 技术栈与汉得 Java 交付体系不匹配；产品模型是"个人助手 + 团队共享"，不是"企业员工目录 + 数据权限"；把它的团队模型改成多租户企业模型，工作量不小于自研薄内核。
- 建议借：① `SKILL.md`/Agent Skills 格式与加载语义；② Gateway/Channel/Node 的分层与 WS 协议设计（尤其幂等键、设备配对、事件模型）；③ ClawHub 的"扫描 + 版本信任判定"市场机制。
- 若要做"个人版兼容"（导入用户已有的 OpenClaw 技能/配置），做一个 **OpenClaw 兼容导入器**即可，不必把运行时绑死。

### B.2 Dify：能力最全，但商业上"不能碰"

**定位**：开源 LLM 应用开发平台，Workflow/Chatflow + RAG + Agent + 插件市场 + BaaS。

**技术栈（据 README/文档，B 级）**：Python/Flask 后端、Next.js 前端、PostgreSQL、Redis、Celery；代码执行在独立的 `dify-sandbox`（Go，1,276★，Apache-2.0）；向量库可接 Weaviate/Qdrant/Milvus 等。

**编排**：可视化 Workflow/Chatflow（DSL 可导入导出）、节点含 LLM/知识检索/代码/HTTP/迭代/循环/参数提取/ Human Input；新 Agent（beta）有自己的沙箱，能跑命令、装软件、读写文件，可作为独立应用或工作流中的一个节点。

**多租户/RBAC（已核验文档）**：Workspace 是租户单位；内置 Owner/Admin/Editor/Normal 四角色；**自定义角色与细粒度资源授权仅 Enterprise**；知识库权限是"整库可访问成员"级别。

**插件/工具市场**：Dify Marketplace（模型、工具、Agent 策略、触发器、Endpoint、数据源），支持 MCP；社区版支持**第三方插件签名校验**（自己生成密钥、签 `.difypkg`、把公钥加入信任列表）——这一点非常值得 DataClaw 抄。

**渠道**：WebApp/嵌入/API/MCP Server。**没有原生飞书/企微/钉钉**，要靠自定义工具或第三方插件。

**可观测**：应用日志、标注、Dashboard；可接 LangSmith/Langfuse/Opik/Phoenix/Weave 等。

**许可（决定性）**：修改版 Apache 2.0，两条附加条件——不得运营多租户环境（tenant=workspace）、不得去前端 LOGO/版权；贡献者还需同意"生产方可调整协议严格程度"。**DataClaw 要白标 + 多租户，等于两条都撞。**

**复用边界**：可以学它的 DSL 设计、插件签名机制、Marketplace 运营；**不能 fork 做商业底座**（除非买商业授权）。

### B.3 Coze Studio：白标最友好，但要赌它的成熟度

**定位**：扣子开发平台的开源核心引擎，一站式可视化 Agent 开发（prompt/RAG/plugin/workflow/knowledge/database）。

**技术栈**：后端 Golang、前端 React/TS，微服务 + DDD；依赖 MySQL/Redis/ES/Milvus/MinIO；Docker Compose 起步。

**编排**：Agent + Workflow + 插件 + 知识库 + 数据库 + 变量；有 Chat SDK/OpenAPI。

**多租户/RBAC**：开源版**没有企业级多租户与 SSO**（据 README 与社区对比，B 级）；README 明确提示公网部署风险：开放注册、代码节点 Python 执行环境、SSRF、部分 API 水平越权。**这意味着它默认假设"内网单租户"。**

**许可**：`LICENSE-APACHE` 是标准 Apache-2.0（已核验原文）——**这是它相对 Dify/FastGPT 最大的优势：可白标、可闭源分发、可商用**。

**风险**：最近 push 2026-07-29，**近三个月没有提交**（截至调研日）；社区版功能与企业级能力之间有断层；把它改成多租户 + 数据权限，工作量不比自研小。

**结论**：如果一定要"fork 一个现成的"，Coze Studio 是许可上唯一干净的选择；但产品成熟度和维护节奏让它更像"高风险期权"，不是稳妥底座。

### B.4 RAGFlow：最强的"文档理解 + 检索"组件

**定位**：RAG 引擎，主打"quality in, quality out"——深度文档解析（DeepDoc：OCR、版面、表格）、模板化切分、知识编译、Agentic Retrieval、带引用回答。

**技术栈**：Python + Go，Elasticsearch/Infinity 作为检索后端，MinIO 存文件，Redis 队列；Docker Compose 部署。

**能力**：复杂 PDF/扫描件/表格解析是它的护城河；支持异构数据源；有 agentic workflow 与模板。

**多租户/RBAC**：有团队/成员/角色概念，但**没有到行/列/字段级的数据权限**（B 级判断）。对 DataClaw 的"文档权限 + 数据权限"只能覆盖前半段。

**许可**：**纯 Apache-2.0（已核验原文）**——可白标、可商用、可闭源衍生。这是它作为"组件"的最大价值。

**复用边界**：**推荐把 RAGFlow 当"解析 + 检索服务"用，不 fork 它的前端与租户模型**。DataClaw 的文档权限在自有网关里判，判完只把有权限的 chunk 喂给检索；或者干脆只用它的 DeepDoc 解析能力（如果拆得出来）。

### B.5 FastGPT：国内商用最多，但许可同样卡脖子

**定位**：知识库 + 工作流 + Agent 的一体化平台，国内 To B 交付常见。

**技术栈**：TypeScript/Next.js，MongoDB + PostgreSQL/pgvector；插件体系（fastgpt-plugin）。

**能力（README 已核验）**：Agent Skill 编排、对话/插件工作流（含基础 RPA 节点）、双向 MCP、知识库混合检索与重排、完整调用链路日志、应用评测、iframe 嵌入、对话记录标注。

**多租户/RBAC**：团队/成员级；更细的权限在企业版。

**许可**：修改版 Apache 2.0——不得运营"similar to the FastGPT"的多租户 SaaS；不得去 LOGO/版权。**与 Dify 同类问题。**

**结论**：作为"能力参照物"很好（它的 Skill 编排与评测设计值得看），作为底座同样被 License 挡住。

### B.6 Bisheng：企业权限模型最完整，最值得"抄作业"

**定位**：面向企业场景的 LLM 应用 DevOps 平台，强调知识空间、任务型 Agent、企业权限。

**技术栈**：Python（FastAPI）+ React；依赖 ES/Milvus/OnlyOffice 等；Docker Compose。

**能力（README 已核验）**：

- **Task Mode**：给目标 → 主 agent 拆任务清单 → 并行子 agent → HITL 暂停等人工 → 产出报告/PPT/Excel/Word；内置 PPT/Excel/Word 技能包，可从本地或 GitHub 导入团队技能；结论带引用标记可回溯。
- **Knowledge Space**：多级文件夹、标签、Owner/Manager/Editor/Viewer 权限模板，权限可到**单个文件**，可按人/部门（含子部门）/用户组授权，默认继承父级；知识广场；超级管理员一键建部门空间。
- **企业特性**：组织/用户/角色/配额；**RBAC + ReBAC**；加入空间/订阅频道/申请菜单权限可走审批流；审计（会话内容 + 系统操作日志，可按人/时间/模块检索）；SSO/LDAP；信创 DM8；Open API 支持"服务账号"与"以员工身份调用"；仪表盘与 DSH 桌面企业接入属商业版。

**许可**：纯 Apache-2.0（已核验）。**但注意 open-core：仪表盘、桌面企业接入等在商业版**——抄架构可以，别指望白拿全部功能。

**结论**：**Bisheng 是 DataClaw 在"企业权限 + 员工任务"这一层最好的老师**。它的 RBAC+ReBAC、权限模板、部门空间、审批、审计，几乎就是 DataClaw"三层理念"的工程实现。建议做一次 2-3 天的源码走读（重点看权限模型与工作流 HITL），不必 fork。

### B.7 MaxKB：够用，但 GPL-3.0 是硬约束

**定位**：基于知识库的智能问答/工作流平台，1Panel 生态，国内装机量大。

**技术栈**：Python/Django。

**许可**：GPL-3.0（已核验原文）。**内部部署没问题；一旦随设备/软件分发，或做闭源商业发行，就会触发源码开放义务**，除非买商业授权。汉得是交付型公司，"交付即分发"，这条要法务重点看。

**结论**：不建议作为 DataClaw 的底座或嵌入组件；可以作为"客户已有 MaxKB，做对接"的适配对象。

### B.8 其余四个：Langflow / Flowise / n8n / Open WebUI

- **Langflow（MIT，155,955★）**：组件化可视化 Flow，Python 生态好，做 POC 极快；但没有多租户、没有企业 RBAC、没有员工模型。**适合内部原型，不适合产品底座**。
- **Flowise（55,520★，已归档）**：Apache-2.0 核心 + enterprise 目录商业许可；**仓库 archived=true，最后 push 2026-08-13**。归档原因我**未核实**，但结论明确：不选。
- **n8n（208,381★，Sustainable Use License）**：400+ 集成、AI Agent 节点、可视化自动化最强；但许可证是 fair-code（非 OSI），`.ee` 文件需企业许可，且**单实例单租户**。适合做"企业系统连接器"的参考，不适合当员工平台。
- **Open WebUI（156,543★，Open WebUI License）**：多用户/角色/分组、知识库、Tools/Pipelines，前端体验极好；但许可证规定超过 50 个终端用户就不得改品牌（除非企业授权），且没有 IM 渠道与 Agent 沙箱。**可作为"前端交互参考"，不能直接白标。**

### B.9 这一节的结论

1. **没有一个开源平台能开箱即用变成 DataClaw**：它们都是"应用/工作流中心"，DataClaw 是"员工/权限中心"。这是产品模型的根本差异，不是功能清单的差异。
2. **许可上真正能白标商用的只有**：Coze Studio、RAGFlow、Bisheng（纯 Apache-2.0）、Langflow（MIT）、OpenHands（MIT）。Dify、FastGPT、MaxKB、Open WebUI、n8n 都有附加约束。
3. **能力上最值得借鉴的**：Bisheng 的权限与 HITL、Dify 的插件签名与 DSL、RAGFlow 的解析、Coze 的插件/工作流交互。
4. **最不该做的**：fork Dify 改多租户 + 去 LOGO。技术债 + 法律风险双杀。

## C. Agent 运行时与沙箱隔离

### C.1 先看"隔离强度谱系"（选型的坐标系）

| 层级 | 代表 | 隔离边界 | 启动/密度 | 兼容性 | 运维复杂度 | 适用 |
|---|---|---|---|---|---|---|
| 进程级 | nsjail、bubblewrap | 内核 namespace + seccomp | 毫秒 / 很高 | 好 | 低 | 单机工具执行、CI |
| 容器级 | Docker 受限容器 | 共享内核 + cgroups/seccomp/cap drop | 百毫秒 / 高 | 最好 | 低 | 开发环境、可信用户 |
| 内核级 | gVisor（runsc） | 用户态内核拦截 syscall | 百毫秒~秒 / 中高 | 有 syscall 缺口 | 中 | K8s 多租户的"够用解" |
| 微 VM（OCI） | Kata Containers | 每 Pod 一个轻量 VM | 秒级 / 中 | OCI 兼容 | 中 | 强隔离 + 标准 K8s |
| 微 VM（专用） | Firecracker | KVM microVM，最小设备模型 | ~百毫秒（快照恢复更快）/ 高 | 需适配 | 高 | 大规模多租户 Agent 沙箱 |
| 本地 microVM | microsandbox | 本机 microVM（libkrun 系） | 快 / 单机 | OCI 镜像 | 低 | 桌面/边缘、单机多租户 |

**判断**：DataClaw 是"每用户独占实例 + 数据不出域 + 企业私有化"，**至少要到内核级（gVisor）或微 VM 级**；Docker 只能用于开发/演示。依据：Dify 自己都承认社区版 Agent 运行时不是"互不信任用户之间的安全边界"，而 DataClaw 的客户恰恰是互不信任的员工。

### C.2 候选逐评

**OpenSandbox（阿里开源，16,093★，Apache-2.0）——最贴合 DataClaw 的一个**

- 本地 Docker 起步，K8s 上用 operator 部署，统一 sandbox 生命周期 API。
- **Fast Sandbox**：Firecracker 创建 **64ms P50 / 125.4ms P99（10 并发）**；支持 pause/resume 且**保留内存与磁盘状态**。
- **出域管控**：per-sandbox egress 策略，FQDN/CIDR/端口规则，DNS 过滤，`dns+nft` 双重默认拒绝，平台可设 `deny.always`/`allow.always` 地板。
- **Credential Vault**：真实凭据只写到 egress sidecar，沙箱内进程只拿到假/空值；工具发起的出站 HTTPS 由 sidecar 匹配注入。**这正好解决 PDF 里"API Key 明文"的痛点。**
- SDK 覆盖 Python/Java-Kotlin/TS/C#/Go，另有 CLI 与 MCP 接入——**Java SDK 对汉得技术栈是加分项**。
- 风险：项目较新（2026 年活跃），大规模生产案例我**未核实**；K8s + Firecracker 需要 KVM 与节点运维能力。

**E2B（14,517★）/ E2B Runtime（1,759★，Apache-2.0）——工程完成度最高的参考**

- 每个 sandbox 一台 Firecracker microVM，独立 cgroup + network namespace；**"创建 sandbox = 恢复快照"**，用 `userfaultfd` 惰性加载内存页，rootfs 是只读镜像上的 CoW overlay；pause 时把内存/磁盘 diff 传到对象存储。
- 每 sandbox 独立 nftables + SNI/Host 检查的域名允许/拒绝列表；secrets 在控制面只存元数据；workload identity 发短期 token；全链路 OTel。
- **判断**：架构是"标准答案"，但自己运维一整套 Firecracker + 快照存储 + 边缘路由，成本很高；除非要卖"沙箱 PaaS"，否则优先用 OpenSandbox 这种更接近"开箱"的方案。

**microsandbox（8,779★，Apache-2.0）**

- 本地 microVM（硬件级隔离）、fork/snapshot、OCI 镜像、`msb` CLI、SDK 直接拉起 microVM，无需基础设施。
- **适用**：单机版 DataClaw（客户现场一台服务器）、桌面端、离线 demo。**不适合**作为集群多租户主方案。

**kubernetes-sigs/agent-sandbox（4,366★，Apache-2.0）**

- 定义 `Sandbox` CRD：有状态、单例、稳定身份、PVC；把隔离委托给 RuntimeClass（gVisor/Kata）。
- **价值**：如果 DataClaw 决定"就用 K8s 原生"，这是最标准的编排层；但它只解决"怎么管沙箱"，不解决"怎么隔离"。

**gVisor（19,757★，Apache-2.0）**

- 用户态内核 + syscall 拦截，`runsc` 作为 RuntimeClass；**部署成本最低的强隔离方案**（不需要 KVM，不需要改镜像）。
- 代价：syscall 兼容性缺口（部分工具/浏览器/GPU 场景会踩坑）、性能开销。**建议作为一期默认，Firecracker 作为二期性能/密度优化。**

**Kata Containers（8,996★，Apache-2.0）**：OCI 兼容 microVM，K8s RuntimeClass 即插即用；比 gVisor 兼容性好、比 Firecracker 运维简单，但启动与密度不如专用方案。**适合作为 gVisor 的备选。**

**Firecracker（37,577★，Apache-2.0）**：microVM 事实标准，但**它只是 VMM**，要自己做 orchestrator、快照、网络、镜像分发——等于重造 OpenSandbox/E2B。**不建议自研这一层。**

**nsjail（4,169★）/ bubblewrap（9,173★，LGPL-2.1）**：进程级沙箱，适合"工具执行"这种短任务；bubblewrap 是 Flatpak 底座，非特权友好，但**不提供 VM 级隔离**。可用于"轻量工具沙箱"兜底，不适合承载"员工工作区"。

**Docker 受限容器 / 每用户 K8s Pod + namespace**：

- Docker：共享内核，配置稍错就逃逸；**只能用于开发/可信租户**。
- K8s 每用户 Pod + NetworkPolicy + ResourceQuota + PVC：工程上最成熟，但**Pod 不是安全边界**，必须配 gVisor/Kata RuntimeClass 才够。

### C.3 会话持久化（"员工的电脑不能每次重装"）

四种做法，建议组合：

| 方案 | 机制 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 卷（PVC/Volume） | 每用户一块盘挂到沙箱 | 简单、可备份 | 冷启动慢、盘会漂移 | 一期默认 |
| 快照/恢复 | pause 时把内存+磁盘 diff 存对象存储（E2B/OpenSandbox） | 秒级恢复、状态完整 | 依赖对象存储与快照格式 | 二期 |
| CoW overlay | 只读基础镜像 + 可写层 | 省空间、启动快 | 层多了会慢 | 镜像/依赖管理 |
| Fork | 从运行中沙箱复制新沙箱（microsandbox/E2B） | 并行试错、评测 | 状态一致性难 | 评测/RL |

**判断**：一期用"PVC + 镜像预热"就够；二期上"pause/resume 快照"，因为 DataClaw 的员工是**长期存在**的（今天配好的技能、记忆、文件，明天还要在），冷启动体验直接决定留存。

### C.4 网络出域管控（数据不出域的关键）

推荐三层：

1. **默认拒绝**：沙箱网络策略默认 deny-all，只放行必需域名/IP。
2. **DNS 白名单 + nftables**：参考 OpenSandbox（DNS 过滤 + `dns+nft` 双重强制）与 E2B（nftables + SNI/Host 检查）。注意 **SNI 检查对 TLS1.3/ECH 有盲区**，不能作为唯一手段。
3. **L7 egress proxy**：所有出站 HTTPS 走代理（Squid/Envoy/自研），做域名 allowlist、方法/路径级策略、DLP 扫描、审计日志。**这是唯一能真正看到"传了什么"的层。**

补充：对"外部信息检索"（销售情报场景）单独开一个"只读公网"的 egress profile，和"访问企业内网"的 profile 物理隔离，避免 prompt injection 把内网数据带出去。

### C.5 凭据管理

- **不要**把 API Key 写进沙箱环境变量或文件（PDF 说的"API Key 明文"就是这么来的）。
- 采用 **sidecar 注入**：沙箱内只见占位符，真实凭据由 egress sidecar 在出站时替换（OpenSandbox Credential Vault 的做法）。
- 短期凭证：Vault/KMS 签发 TTL 15-60 分钟的 token；workload identity（SPIFFE/SVID 思路）绑定"员工-会话-沙箱"三元组。
- 审计：每次凭据使用记"谁的身份、为哪个员工、访问了哪个域、返回码"，不记明文。

### C.6 HITL（人在环）实现范式

企业场景的 HITL 不是"弹个确认框"，而是**可审计的审批状态机**：

1. **风险分级**：工具调用前打标（只读/写/外发/资金/删除），高风险默认拒绝。
2. **策略判定**：OPA/Casbin 判"这个员工 + 这个技能 + 这个参数"是否需要审批、审批人是谁、是否要四眼。
3. **暂停与恢复**：工作流持久化（Temporal 或自研状态机 + DB），暂停时保存完整上下文；恢复必须幂等（用 runId + stepId 去重）。
4. **审批留痕**：审批人、时间、理由、看到的证据（SQL/文件 diff/收件人），全部进审计。
5. **超时默认拒绝**，不能"超时自动通过"。

参考实现：Bisheng 的审批流 + HITL 工作流节点、Dify 的 Human Input 节点、OpenClaw 的 approval 机制（deny 优先、校验失败即拒绝）。

### C.7 运行时推荐组合

- **一期（3 个月内）**：K8s + **agent-sandbox CRD**（或原生 StatefulSet）+ **gVisor RuntimeClass** + PVC + NetworkPolicy + egress proxy。理由：不依赖 KVM、交付简单、隔离达标。
- **二期（性能/密度）**：**OpenSandbox**（Firecracker Fast Sandbox + pause/resume + Credential Vault + egress 策略），把"每用户独占实例"做成"预热池 + 按需恢复"。
- **单机/离线版**：**microsandbox** 或 Docker + gVisor（视客户环境）。
- **不选**：自研 Firecracker 编排（成本无底）、纯 Docker（不安全）、nsjail/bubblewrap 承载员工工作区（隔离不够）。

## D. MCP 与技能生态

### D.1 MCP 规范要点（2026-07-28 版，已核验）

- **协议**：JSON-RPC 2.0；传输两种——**stdio**（newline-delimited JSON-RPC）与 **Streamable HTTP**（POST + 可选 SSE 流；旧的独立 HTTP+SSE 已被取代）。
- **服务端能力**：Tools（模型可调用的函数）、Resources（上下文数据）、Prompts（模板化消息/工作流）。
- **客户端能力**：Roots（文件系统边界）、Sampling（服务端请求模型采样）、Elicitation（向用户追问）。
- **授权**：可选；HTTP 传输用 OAuth 2.1 风格（授权服务器发现、客户端注册、scope 选择、资源指示器、**step-up authorization** 增量授权）。
- **许可**：MCP 项目正从 MIT 迁移到 **Apache-2.0**，规范文档 **CC-BY-4.0**。

**对 DataClaw 的含义**：把"企业系统连接器"做成 MCP server（ERP/CRM/OA/数仓各一个），把"DataClaw 能力"也暴露成 MCP server（让客户自己的 IDE/Agent 能调），是低成本生态策略；但**MCP 的授权是传输层 OAuth，不等于数据权限**——行列级仍要在自己的查询网关里做。

### D.3 SKILL.md / Agent Skills 规范（已核验 agentskills.io）

- 目录结构：`skill-name/SKILL.md` + 可选脚本/资源。
- frontmatter：`name`（必填，≤64，小写字母/数字/连字符，不以连字符开头结尾）、`description`（必填，≤1024，必须同时说明"做什么"和"什么时候用"）、`license`（可选）、`allowed-tools`（可选，实验性，空格分隔的预授权工具）。
- **渐进披露**：启动时只加载 name+description（约 100 token/技能）→ 触发后读 SKILL.md 正文（<5k token）→ 需要时再读引用文件/跑脚本（脚本代码不进上下文）。
- 生态现状：Anthropic 的 `anthropics/skills` 仓库 183,186★，但 **GitHub API 检测不到标准 License**（license=None）——**技能内容不能默认 MIT**，商用前要逐目录看声明或取得授权。

### D.4 企业技能市场的设计（DataClaw 该怎么做）

把"技能"当"软件包"治理，六件事缺一不可：

1. **清单（manifest）**：在 SKILL.md 之外加企业字段——权限声明（要访问哪些数据源/表/列）、网络出域域名、需要的密钥、可执行文件、资源限额、适用角色。
2. **签名**：cosign/minisign 签包，公钥进租户信任列表；参考 Dify 社区版的"第三方签名校验"（生成密钥 → 签 `.difypkg` → 公钥加入白名单）。
3. **扫描**：ClamAV/YARA + 静态分析（可疑网络调用、文件访问、命令执行）+ 依赖 SBOM；参考 ClawHub 的 VirusTotal + ClawScan，但**不要允许"扫描未完成带警告安装"**——企业版应默认拒绝。
4. **审核**：管理员审核 + 分级（官方/认证伙伴/内部自建/个人），个人技能默认只能自己用。
5. **版本与灰度**：技能版本锁定到员工/会话；升级走灰度 + 可回滚；`openclaw skills verify` 的教训是**必须 hash 本地文件**，不能只信注册中心信封。
6. **运行时约束**：技能只能在沙箱里跑，出域走 egress 策略，密钥走 vault 注入；高危技能强制 HITL。

## E. 数据权限与安全（DataClaw 的护城河）

### E.1 分层模型（对客户讲得清，对研发拆得开）

| 层 | 管什么 | 实现 |
|---|---|---|
| L1 身份 | 谁是员工、属于哪个部门、什么角色 | 对接企业 IdP（LDAP/AD/OAuth/OIDC），员工-角色-部门三元组 |

| L5 值 | 敏感值怎么处理 | 掩码/hash/替换/截断/加密；分级分类驱动 |
| L6 审计 | 谁在什么时候看了什么 | 结构化事件 + 不可篡改存储 + 检索 |

### E.3 "sqlglot 查询前 AST 级行列权限注入 + 脱敏重写"的可行性与坑

**结论：可行，而且是当前最优解；但必须配"查询网关 + 失败拒绝 + 结果兜底"，不能单靠它。**

**做法（参考 AskTable 的公开实践）**：

1. 用 `sqlglot.parse(sql, dialect=...)` 解析成 AST。
2. 用 `Scope` 遍历：`scope.derived_table_scopes`（派生表）、`scope.cte_scopes`（CTE）、`scope.subquery_scopes`（WHERE/HAVING 子查询）、`union_scopes`。
3. 对每个"表引用"注入行谓词（如 `AND tenant_id = :ctx_tenant AND dept_id IN (...)`），对每个"输出列"做列裁剪/脱敏函数替换。
4. 生成 SQL 下推执行。

**坑点清单（按踩坑概率排序）**：

| 坑 | 说明 | 应对 |
|---|---|---|
| 别名识别 | `FROM orders o` vs `FROM orders`，注入条件挂错对象 | 用 `source.alias != source.name` 判断真实别名；以 Scope 的表源为准，不用字符串拼 |
| 同表多次出现 | 自连接/子查询重复注入 | 按 Scope + 表身份去重，不要按 SQL 字符串去重（会把不同作用域误判为同一条） |
| `SELECT *` | 无法做列级脱敏 | 展开为显式列清单（依赖元数据）；元数据缺失时拒绝而非放行 |
| 方言 | MySQL 反引号 / PG 双引号 / Oracle 大写 | 统一用 sqlglot 的 `dialect` 处理标识符引号，禁止手工拼 |
| CTE / UNION / 窗口函数 | 谓词注入位置错会导致语义变化 | 逐 Scope 注入；UNION 每个分支都要注入；窗口函数先注入再计算 |
| 视图/存储过程 | 视图内部绕不过去 | 禁止直连视图/存储过程，或为视图建"安全视图" |
| 函数/不可下推 | 脱敏函数在 DB 不支持 | 结果集二次脱敏兜底 |
| 语义等价 | 改写后结果变多/变少 | 建立"改写前后行数/校验和"对比测试集；上线前回归 |
| 性能 | 每查询多一次 parse+rewrite | 目标 <10ms（公开实践值）；加 SQL 指纹缓存；复杂 SQL 走异步 |
| 降级 | 改写失败怎么办 | **默认拒绝**（fail-closed），日志告警；绝不能"失败就放行"或"让 LLM 改 SQL 兜底" |
| 绕过 | 用户直连 DB / 用别的客户端 | 网络层只允许网关访问 DB；DB 账号只给网关；定期扫描直连 |

**为什么不用 JSqlParser/Calcite**：JSqlParser 只给 AST，没有作用域解析，CTE/子查询/别名的活要自己写，工作量翻倍；Calcite 有完整校验但重，且与"改写后下推"的工程链路不如 sqlglot 顺手。**建议 Python sidecar 跑 sqlglot**（Java 主服务通过 gRPC/HTTP 调），这是"用对工具"而不是"技术栈纯粹"。

**必须补的三件事**：

- **策略服务**：OPA（Rego）或 Casbin 存"员工-表-列-行"策略，查询网关只做执行点；策略变更要能热更新 + 版本化。
- **结果兜底**：即使 SQL 改写成功，返回前再按列策略做一次脱敏（防 `SELECT *`、防函数绕过）。
- **审计**：记录原始 SQL、改写后 SQL、命中策略、返回行数、耗时、操作人；原始 SQL 与结果摘要进不可篡改存储。

### E.4 脱敏与敏感识别

- **脱敏算法**：掩码（保留首尾）、hash（不可逆，用于关联）、替换（假名化）、截断、加密（可逆，需 KMS）。策略按"数据分级 × 角色"配置，参考 PDF 的 mask/hash/替换/截断四类。
- **敏感识别**：Presidio 的 analyzer（正则 + 校验位 + NER）+ anonymizer 可用；**中文人名/地址/机构名 NER 较弱**，需要补中文规则（身份证、手机号、银行卡、统一社会信用代码）+ 可选 LLM 辅助；识别结果写进元数据（OpenMetadata/DataHub 的 tag/classification），供策略引用。
- **分级分类**：公开/内部/秘密/机密四级，映射到"能不能出域、能不能给 Agent 看、能不能进模型上下文"。

### E.5 审计日志

- **结构化**：`who`（员工/角色/部门）、`what`（员工/技能/工具/数据源/表/列）、`when`、`policy_id`、`decision`、`row_count`、`sql_hash`、`trace_id`。
- **不可篡改**：append-only 存储（ClickHouse/Loki + 对象存储 WORM）+ 哈希链；保留期按合规要求（金融常见 6 个月~3 年）。
- **可检索**：按人/部门/技能/数据源/时间检索；支持"导出某员工全部数据访问记录"（离职审计）。
- **可观测**：OTel 打通 trace/metrics/logs，工具调用与模型调用同一条 trace。

### E.6 目标架构（数据面）

```
员工 → Channel/Web → 会话服务 → Agent 编排 → 工具/技能
                                        │
                                        ├─ 查询网关（sqlglot 改写 + 策略判定 + 结果脱敏）
                                        │      ├─ OPA/Casbin 策略服务
                                        │      └─ 审计总线（OTel → ClickHouse）
                                        ├─ RAG（文档权限过滤后再检索）
                                        └─ 沙箱（OpenSandbox/gVisor + egress + vault）
```

**关键原则**：**权限判定在网关，执行也在网关；任何"绕过网关直连数据源"的路径都必须被网络策略堵死。**

### F.2 判断：不要"让 LLM 自由写 SQL 打生产库"

DataClaw 的"一句话 → 多维大屏 + 分析报告"，正确的工程链路是：

1. **语义层**：指标、维度、口径、join 关系、枚举、单位，全部 YAML/Markdown 化（WrenAI 的 MDL 思路），进 Git、可 review。
2. **意图 → 查询计划**：LLM 只负责"选指标/维度/过滤条件"，生成结构化查询计划，不直接写 SQL。
3. **计划 → SQL**：由语义层编译器生成 SQL（或让 LLM 生成后经 sqlglot 校验 + 语义层校验 + dry-run）。
4. **执行**：过数据权限网关（E 节）。
5. **呈现**：图表模板库（ECharts option 模板）+ LLM 只填数据与文案；大屏用固定布局模板，避免"每次生成都不一样"。
6. **报告**：结论必须带"数据来源 + 查询时间 + 口径"脚注，可点开看明细。

**依据**：WrenAI 的卖点就是"governed SQL + dry-plan 校验 + 行数限制"，说明业界已经验证"纯 LLM 写 SQL 不可控"；DataClaw 若跳过语义层，工时分析场景一定会在"口径对不上"上翻车。

### F.3 大屏与嵌入

- 图表：ECharts（Apache-2.0，中文文档好，汉得前端团队上手快）。
- 大屏：固定布局模板 + 数据绑定；不要用"AI 生成 HTML 大屏"作为生产方案（不可维护、不可审计）。
- 嵌入：iframe + postMessage 或 Superset Embedded SDK；对外交付优先 iframe（隔离好、升级不影响宿主）。
- 移动端：同一套图表配置出 H5，避免两套代码。

### G.2 合同审查的工程要点

1. **自适应解析**：PDF（文本层/扫描件）、Word（含修订/批注）、图片；先判类型再选 pipeline；扫描件走 OCR + 版面。
2. **结构化**：条款树（章/条/款）、表格、甲乙方、金额、日期、违约责任；用"规则 + LLM"双通道，LLM 输出必须带页码/坐标。
3. **企业规则库**：把"公司合同规范"做成可配置规则（必须包含的条款、禁止的表述、金额上限、管辖地），跨页比对。
4. **风险分级**：高/中/低 + 依据（引用原文 + 规则 id），不允许"无依据的风险"。
5. **输出修订版**：Word 用 **OOXML 修订痕迹**（`w:ins`/`w:del`，删除文本放 `w:delText`，带 `w:author`/`w:date`），让法务在 Word 里"接受/拒绝修订"；PDF 用批注（注释框）。
6. **可回溯**：每条风险能跳到原文位置；修订版能 diff 出"改了什么、为什么"。

### G.3 Word 修订痕迹：库与坑

- `python-docx`（MIT，5,750★）**不支持修订痕迹**；需要 `docx-revisions`（18★，MIT，给 python-docx 补 `<w:ins>/<w:del>` 读写）或直接操作 OOXML（lxml）。
- 坑：
  - 删除的文本必须放 `w:delText` 而不是 `w:t`，否则 Word 打不开或显示异常。
  - 段落标记的插入/删除用 `w:rPr/w:ins`、`w:rPr/w:del`。
  - 表格单元格、页眉页脚、脚注、批注里的修订要单独处理。
  - `w:id` 要唯一；`w:author`/`w:date` 必填，否则"接受/拒绝修订"体验差。
  - 生成后必须用 Word/WPS 实际打开验证（accept all / reject all 各一遍），不能只看 XML。
- PDF 批注：PyMuPDF 最方便但 AGPL；替代是 pdf.js（前端高亮）+ 自研批注数据层，或 pypdf（BSD，能力弱）。**建议 PDF 只做"高亮 + 侧栏批注"，不承诺"生成可编辑修订版 PDF"。**

## H. 渠道接入（飞书/企微/钉钉）

### H.1 三家对比（已核验部分 + 未核实标注）

| 维度 | 飞书 | 企业微信 | 钉钉 |
|---|---|---|---|
| 机器人入站 | 事件订阅（webhook）或**长连接**模式 | 群机器人只能发；入站需自建应用回调 | 机器人 webhook；Stream 模式可免公网 |
| 回调加密 | Encrypt Key（AES）+ Verification Token；URL 校验 challenge | AES msg_encrypt + 签名 | AES + 签名（具体字段名以文档为准） |
| 主动消息额度 | 官方按应用/租户设配额（**具体数值未核实**） | 群机器人 **20 条/分钟**；应用消息：每应用 ≤ 账号上限×200 人次/天，同一成员 ≤30 次/分钟、1000 次/小时（已核验） | 官方有频率限制（**具体数值未核实**） |
| 交互卡片 | 支持（卡片回调） | 支持（模板卡片） | 支持（互动卡片） |
| 组织架构 | 通讯录 API | 通讯录/部门 API | 通讯录 API |
| 开源 SDK | larksuite/oapi-sdk-java（313★，Apache-2.0） | 官方 SDK（多语言） | dingtalk-stream-sdk-python（176★，MIT）等 |
| 工程难点 | 3 秒响应/重推、加解密、长连接保活 | 回调验签、额度、会话存档 | Stream 模式、卡片状态机 |

> 说明：飞书文档站是 SPA，正文没取到；钉钉帮助站 TLS 握手被阻断。表中"未核实"的数字请在接入前用官方文档复核，**不要写进对客承诺**。

### H.2 统一渠道适配层（建议）

```
Channel Adapter（每家一个实现）
  ├─ 验签/解密
  ├─ 事件归一化（消息/卡片回调/进群/菜单）
  ├─ 幂等（event_id 去重）
  ├─ 限流（按租户/机器人/会话）
  ├─ 回复（文本/卡片/文件）
  └─ 审计（谁在哪个群、问了什么）
```

**关键设计**：

- **主动消息一定要排队 + 限流 + 合并**：企微 20 条/分钟是硬顶，日报/告警一多就被丢；用"聚合卡片 + 摘要 + 链接"代替逐条推送。
- **长连接优先**：飞书/钉钉都支持长连接模式，能省公网回调、省证书、省 WAF；私有化交付尤其合适。
- **卡片即 UI**：审批、确认、选参数都用卡片按钮回调，不要把用户引到 H5（流失率高）。
- **群 vs 单聊**：群里的回答要"@提问者 + 引用原消息"，否则多人场景会乱。
- **组织架构同步**：员工入职/离职/转部门要同步到 DataClaw 的员工目录与权限，否则"离职即带走"防不住。

### I.3 明确推荐：路线 ②

**推荐理由（三条）**：

1. **产品模型匹配**：DataClaw 的核心对象是"员工/角色/技能/权限/审计"，不是"应用/工作流"。自研薄内核才能把"公共员工模板 → 版本 → 分配 → 回收"做顺；fork 任何平台都要先拆掉它的应用中心模型。
2. **法律与交付安全**：只用 Apache-2.0/MIT 组件（OpenSandbox、RAGFlow、Docling、sqlglot、ECharts、OPA、Casbin），可白标、可闭源分发、可私有化；不碰 Dify/FastGPT 的附加条款。
3. **护城河在数据面**：真正难被抄的是"行列级权限 + 脱敏 + 审计 + 语义层口径"，这些本来就要自研；把有限人力投在这里，比改 Dify 的租户模型回报高。

**分期路线图（建议）**

| 阶段 | 时间 | 交付 | 关键验证 |
|---|---|---|---|
| P0 技术验证 | 2 周 | sqlglot 改写 PoC（5 类 SQL：join/子查询/CTE/UNION/窗口）+ gVisor 沙箱 + 飞书长连接 | 改写正确率、沙箱逃逸测试、渠道连通 |
| P1 MVP | 10-12 周 | 员工/会话/技能/SKILL.md 导入、3 个标杆场景（工时/销售/合同）各 1 条链路、基础审计 | 3 个客户 POC 跑通；单员工隔离验证 |
| P2 企业化 | 5-6 个月 | 行列级权限、脱敏、审批 HITL、技能市场（签名/审核/版本）、结算计量、OpenSandbox 快照 | 等保/渗透测试；500 员工压测 |
| P3 生态 | 持续 | MCP 网关、开放 API、伙伴技能、行业模板 | 伙伴接入数、技能复用率 |

**团队配置建议（P1）**：Java 后端 3（会话/员工/权限/渠道）、Python 1-2（解析/SQL 改写/模型编排）、前端 2（员工台/大屏/管理端）、测试 1、产品/交付 1。

### I.4 风险与止损点

| 风险 | 触发信号 | 止损动作 |
|---|---|---|
| sqlglot 改写覆盖不了客户 SQL | 复杂 SQL 改写失败率 >5% | 降级为"安全视图 + 查询模板"，限制自由 SQL；仍失败则只开放预置指标 |
| 沙箱性能/密度不达标 | 单节点 <30 并发、启动 >3s | 一期 gVisor 扩容；二期 OpenSandbox 预热池；仍不行则"每部门共享沙箱 + 强审计" |

| 客户要"像 Dify 一样的编排器" | 3 个以上客户提 | 提供"高级模式"：把工作流 DSL 作为可选能力，内核仍是员工模型 |

## J. 对本项目二次开发的 10 条落地建议

1. **先定"员工"的对象模型，再写代码**：员工 = 模板（角色/SOUL/技能集/记忆开关）+ 实例（人/部门）+ 版本 + 分配关系 + 回收策略。这个模型定错，后面全返工。
2. **把"权限"做成独立服务，不要散在业务里**：一个策略服务（OPA/Casbin）+ 一个查询网关（sqlglot）+ 一个文档权限服务，三者用统一主体（员工/角色/部门）和统一资源 id。
3. **技能包从第一天就签名 + 版本锁定**：SKILL.md 兼容 Agent Skills，但企业 manifest 必须有"权限声明/出域域名/密钥需求"；安装前 hash 校验，禁止"带警告安装"。
4. **沙箱不要自研**：一期 gVisor + K8s，二期 OpenSandbox；把精力放在"预热池、快照、出域策略、凭据注入"的集成上，而不是 VMM。
5. **所有工具调用走统一执行器**：超时、重试、幂等、限流、审计、脱敏、HITL 都在这一层做；不要让每个技能自己调 HTTP。
6. **语义层先行的 BI**：工时/销售场景先把指标口径 YAML 化，LLM 只选指标和维度；大屏用模板，不做"AI 生成页面"。
7. **合同审查先做"规则库 + 引用"**：没有规则库的合同审查就是"聊天"，客户不会买单；每条风险必须能点回原文。
8. **渠道层按"适配器 + 归一化事件"设计**：飞书/企微/钉钉各一个 adapter，统一成 message/card/approval 三类事件；主动消息一律排队聚合。
9. **审计按"合规产品"做，不是按"日志"做**：谁、什么权限、查了什么、改了什么、谁批的，一条链可导出；保留期可配置。
10. **保留"OpenClaw 兼容导入"作为增长手段**：让客户/极客用户把个人版技能、SOUL、渠道配置导入企业版，降低迁移门槛；但运行时不要绑死 OpenClaw。
